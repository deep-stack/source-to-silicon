From main.cpp to electrons: how C++ really runs

We'll follow one small program from the source file through preprocessing, parsing, IR, optimization, instruction selection, the assembler, object files, the linker, the dynamic loader, the kernel's execve, virtual memory, the out-of-order core that runs it, and the operating system that shares that core between threads. Every listing in this guide is real output from the toolchain on an Ubuntu 24.04 machine. None of it is invented for illustration.

CHAPTER 00

The whole pipeline on one page

"Compiling" is really about a dozen separate transformations, each with its own data structure. Here's the map. The rest of the guide walks through it left to right, then top to bottom.

The running example

Three small files, chosen so that each one exercises something interesting: a function defined in another translation unit (TU), a global variable defined elsewhere, a function template instantiated in the header, a file-local static, a string literal, and a call into the C library.

math.h
#pragma once
int square(int x);
extern int counter;
template <typename T>
T add(T a, T b) { return a + b; }
math.cpp
#include "math.h"
int counter = 0;
int square(int x) {
    ++counter;
    return x * x;
}
main.cpp
#include <cstdio>
#include "math.h"

static const char* greeting = "result";

int main() {
    int r = square(7) + add(1, 2);
    std::printf("%s: %d (calls=%d)\n",
                greeting, r, counter);
    return 0;
}
$ g++ -O0 main.cpp math.cpp -o app
$ ./app
result: 52 (calls=1)

Building this one program touches every concept in this guide. When main.cpp is compiled, the compiler doesn't know where square or counter will live. add<int> may be generated in several object files. printf sits in a shared library that won't be mapped into memory until run time, and at an address that changes on every run.

CHAPTER 01

The compiler driver: g++ isn't the compiler

In brief

When you type g++ main.cpp math.cpp -o app, g++ doesn't compile anything itself. It's a driver that runs three separate programs in turn: the compiler proper turns each .cpp into assembly, the assembler turns assembly into an object file, and the linker combines the object files and libraries into one executable.

Each .cpp is compiled completely on its own, as a translation unit. That single fact explains headers, extern, and why a linker is needed at all.

Deep diveHow it works, in detail

g++ and clang++ are drivers. A driver decides which tools to run, in what order, with which flags, and where the temporary files go. -### prints the plan without running it (output trimmed):

CHAPTER 02 · FRONT END

Preprocessing: text in, tokens out

In brief

Before any C++ is understood, the preprocessor does text substitution. It pastes in every #included file, expands macros, and evaluates #if. Our 9-line main.cpp becomes 1,066 lines, almost all of it from <cstdio>.

The output is one long stream of tokens. Repeating this for every file is the main reason C++ builds are slow, and the problem C++20 modules were designed to solve.

Deep diveHow it works, in detail

The C++ standard defines translation as a series of numbered phases ([lex.phases]). The first few are pure text munging, before any C++ grammar applies:

  1. Character mapping. Source bytes are decoded into the translation character set (UTF-8 is mandated as a supported encoding from C++23).
  2. Line splicing. Every backslash-newline pair is deleted, joining physical lines into logical lines.
  3. Tokenization into preprocessing tokens. Each comment becomes a single space. Identifiers, numbers (pp-numbers, which are deliberately loose: 0x1e+1 is a single pp-token), string and character literals, and punctuators are split out.
  4. Directives and macro expansion. #include recursively runs phases 1–4 on the named file and pastes the resulting tokens in. #define, #if and _Pragma are handled here.
  5. Later phases cover literal encoding, adjacent string-literal concatenation ("a" "b" → "ab"), conversion of pp-tokens into real tokens and, finally, the actual "translation" (parsing and semantic analysis), template instantiation and linking.

The preprocessor has no idea what a type, function or scope is. It works on tokens. Our 9-line main.cpp becomes this:

The # 3 "main.cpp" 2 lines are line markers: # linenum "file" flags. Flag 1 means "entering a new file", 2 means "returning to this file", 3 means "this is a system header" (which suppresses warnings) and 4 means "wrap in extern "C"". They're how diagnostics and debug info point at the right file and line even though the compiler proper sees one giant token stream.

Deep diveMacro expansion, precisely
  • Object-like (#define N 10) and function-like (#define MAX(a,b) ((a)>(b)?(a):(b))) macros substitute token sequences. Arguments are fully macro-expanded before substitution, unless they're the operand of # (stringize) or ## (token paste).
  • After substitution, the result is rescanned for more macros. To stop infinite recursion, each token remembers which macros it came from (its hide set, sometimes called "painted blue"). A macro name that turns up inside its own expansion is never expanded again.
  • __LINE__, __FILE__, __COUNTER__ and __has_include are built-in. g++ -dM -E -x c++ /dev/null dumps the ~400 predefined macros, such as __x86_64__, __GNUC__ and __cplusplus.
Deep diveWhy it's slow, and what's replacing it

Every TU re-lexes and re-parses every header it includes. A file that includes <iostream>, <vector> and <string> easily expands to tens of thousands of lines, and a project with 1,000 TUs does that 1,000 times. The fixes, roughly in historical order:

  • Include guards and #pragma once. Both GCC and Clang detect the guard idiom and skip re-opening the file entirely.
  • Precompiled headers (PCH). The compiler serializes its post-parse state (the AST or tree) to disk.
  • C++20 modules. import std; loads a compiled interface (a BMI: a .pcm for Clang, a .gcm for GCC) and doesn't paste text. Macros don't leak across module boundaries, and declarations are parsed once per build instead of once per TU.
CHAPTER 03 · FRONT END

Front end: lexing, parsing and semantic analysis

In brief

The front end reads the token stream and works out what the program means. It parses the tokens into a tree (the AST), then checks it: it resolves every name to a declaration, picks the right overload, fills in templates for concrete types, and inserts the conversions the language implies.

This is where compile errors come from, and it's the hardest part of a C++ compiler, because C++ can't even be parsed without knowing what each name refers to.

Deep diveLexing

The lexer turns characters into tokens: kw_int, identifier("square"), l_paren, numeric_constant("7") and so on. It follows the maximal munch rule (the longest valid token wins), so a+++b is a ++ + b. There's one famous carve-out: since C++11, >> closes two template argument lists in vector<vector<int>>, and the parser splits the token back apart. Clang produces tokens on demand as the parser asks (clang -Xclang -dump-tokens). It doesn't materialize a token array.

Deep diveParsing: C++ is not context-free

Both GCC and Clang use hand-written recursive-descent parsers. GCC's C++ front end abandoned its yacc grammar in GCC 3.4. They do it by hand because C++ can't be parsed without knowing what names mean:

a * b;          // declaration of pointer b if 'a' names a type; a multiplication otherwise
f(x)(y);        // call result called again, OR declaration of x as function returning … if f is a type
Widget w();     // "most vexing parse": declares a FUNCTION w returning Widget, not an object
T::value * p;   // in a template: multiplication, unless you write 'typename T::value * p;'
x.template get<0>();  // 'template' disambiguator needed when x's type is dependent

So the parser and the semantic analyzer are interleaved. As each declaration is parsed it's entered into a scope, and later lookups decide how ambiguous constructs parse. When a construct really is ambiguous, Clang uses tentative parsing: it tries the declaration interpretation, backtracks, and uses the standard's rule that "anything that can be a declaration is a declaration".

Deep diveSemantic analysis (Sema): where C++ gets hard

Name lookup

Unqualified lookup walks scopes outward. Qualified lookup (std::printf) searches a named scope. Argument-dependent lookup (ADL) also searches the namespaces of the argument types. That's why std::cout << x finds std::operator<< without any qualification.

Overload resolution

Lookup builds a candidate set, which gets filtered to viable functions (right arity, with an implicit conversion available for each argument). Each conversion is ranked: exact match, then promotion, then standard conversion, then user-defined, then ellipsis. A function wins only if it's no worse on every argument and strictly better on at least one; otherwise the call is ambiguous.

Templates

Two-phase lookup: non-dependent names are bound where the template is defined, and dependent names where it's instantiated. When main.cpp calls add(1, 2), deduction gives T = int. Sema then instantiates a brand-new FunctionDecl add<int> by substituting into the template's AST, and that instance is compiled like ordinary code. SFINAE and C++20 requires clauses remove candidates whose substitution fails.

Constant evaluation

constexpr/consteval code runs inside the compiler. Clang's evaluator interprets the AST directly (a newer bytecode interpreter is available behind -fexperimental-new-constant-interpreter), and GCC's runs on its trees. It must detect undefined behaviour, so an overflow in a constant expression is a hard error.

Implicit members

Sema implicitly declares default and copy/move constructors, assignment operators and destructors, and defines them only if they're odr-used. It also inserts implicit conversions, temporaries and their destructors (ExprWithCleanups), and binds references.

Layout

Class layout (field offsets, padding, the vptr, base subobjects) is computed per the platform's C++ ABI (Itanium on Linux, MSVC on Windows). clang -Xclang -fdump-record-layouts shows it.

GCC has the same stages with different names. The C++ front end (gcc/cp/) builds GENERIC trees, which are lowered to GIMPLE (see chapter 05). Clang's AST is handed to CodeGen (clang/lib/CodeGen), which walks it and emits LLVM IR.

CHAPTER 04 · FRONT END

Name mangling and the Itanium C++ ABI

In brief

Object files only understand flat names, but C++ allows several functions called square in different namespaces and with different parameter types. So the compiler encodes the full signature into the name: square(int) becomes _Z6squarei.

The encoding is part of a shared rulebook, the Itanium C++ ABI, which is why code compiled by GCC and Clang can link together.

Deep diveHow it works, in detail

Object files and linkers only understand flat strings: a symbol is a name and an address. C++ has overloading, namespaces, classes, templates and const-qualified member functions, so square(int) and square(double) must become different strings. The Itanium C++ ABI, used by GCC and Clang on every non-Windows platform, specifies the encoding exactly. It's why GCC and Clang objects link together.

The ABI is much more than mangling The Itanium ABI also fixes class layout, vtable layout, RTTI structures, the exception-handling interface (__cxa_throw, personality routines), guard variables for local statics, and how constructors and destructors are split into variants. It sits on top of the platform psABI (System V AMD64), which defines the calling convention, register usage, stack alignment, ELF relocation types and the TLS model. Two compilers interoperate only if they agree on both. libstdc++'s std::string layout change in GCC 5 (the "dual ABI", std::__cxx11::basic_string) is the classic example of what happens when a library breaks binary compatibility.
CHAPTER 05 · MIDDLE END

Intermediate representations

In brief

The compiler translates the checked program into an intermediate representation (IR): a simple, regular language between C++ and machine code. Optimizers work on it because it has few constructs and makes data flow explicit.

The key idea is SSA: every value is assigned exactly once, and control flow is a graph of basic blocks. Where paths merge, a φ-node picks the right value.

Deep diveHow it works, in detail

An AST is great for type checking and terrible for optimization: too many node kinds, nested expressions and implicit control flow. Compilers lower it into a small, regular intermediate representation, usually in static single assignment (SSA) form, where every value is assigned exactly once. Real compilers use a ladder of IRs, each closer to the machine:

Deep diveLLVM IR, at -O0 versus -O2

At -O0, Clang's CodeGen deliberately emits naïve IR. Every local variable, including parameters, gets a stack slot (alloca), and every use is a load/store. That makes CodeGen trivial and keeps every variable visible to the debugger.

The mem2reg / SROA pass promoted the alloca into an SSA register: %0 is used directly. The vocabulary here carries real semantics:

%N, @name
Local SSA values and globals. A global's value is its address, which is why @counter has type ptr.
nsw
"No signed wrap". C++ signed overflow is UB, so the frontend tells the optimizer that overflow yields poison, a value that is allowed to be anything. This lets i + 1 > i fold to true.
noundef
The value isn't undefined or poison. Passing an uninitialized int would be UB.
dso_local
The symbol resolves inside this linked module (DSO), so it can be reached PC-relative with no GOT. More in chapter 16.
local_unnamed_addr
The function's address isn't significant within this module, so identical functions may be merged.
!tbaa
Type-based alias analysis metadata. A store through an int* can't modify a float: the "strict aliasing" rule, made machine-readable.

Deep diveSSA, control flow and φ-nodes

A function is a control-flow graph (CFG) of basic blocks: straight-line instruction sequences, each ending in exactly one terminator (br, ret, switch, invoke). When a variable gets different values on different incoming paths, SSA merges them with a φ (phi) node. Here's a real loop:

int sum(const int* a, int n) {
    int s = 0;
    for (int i = 0; i < n; ++i)
        s += a[i];
    return s;
}

Each phi [v, %pred] means "if we arrived from block %pred, the value is v". %9 is i and %10 is s. The induction variable was widened to i64: signed overflow can't happen, so the 32-bit i can safely become a 64-bit pointer offset without re-sign-extending on every iteration.

  %3 = icmp sgt i32 %1, 0
  br i1 %3, label %4, label %6

  %5 = zext nneg i32 %1 to i64
  br label %8

  %7 = phi i32 [ 0, %2 ], [ %13, %8 ]
  ret i32 %7

  %9 = phi i64 [ 0, %4 ], [ %14, %8 ]

  %12 = load i32, ptr %11, align 4
  %13 = add nsw i32 %12, %10
  %14 = add nuw nsw i64 %9, 1
  %15 = icmp eq i64 %14, %5
  br i1 %15, label %6, label %8

Why does SSA matter so much? With one definition per name, every use points straight at its definition (a "use-def chain"). Constant propagation, dead-code elimination, value numbering and register allocation all become sparse, near-linear algorithms instead of iterative dataflow over whole bitsets. Placing φ-nodes minimally uses dominance frontiers (Cytron et al., 1991). Block A dominates B if every path from the entry to B goes through A.

CHAPTER 06 · MIDDLE END

The optimizer: a pipeline of passes

In brief

The optimizer is a pipeline of small transformations ("passes") over the IR. Each pass keeps the program's meaning but makes it cheaper. The most important pass is inlining: copying a called function's body into its caller, which lets every other pass see more.

In our program, inlining turned add(1, 2) into the constant 3. The optimizer also assumes your code has no undefined behaviour, and that assumption is a big part of why it can be so aggressive.

Deep diveHow it works, in detail

An optimizer is a sequence of passes, each a small transformation that preserves semantics, run by a pass manager. LLVM's -O2 pipeline runs well over a hundred pass invocations (clang -O2 -mllvm -print-pipeline-passes), and many passes run several times because each one exposes opportunities for the next. The important ones:

PassWhat it does
SROA / mem2regBreaks aggregates into scalars and promotes stack slots to SSA registers. This is what eliminated the alloca above.

Width 4 means four 32-bit ints per 128-bit SSE register, and "interleaved 2" means two independent accumulators to hide the add latency. That gives 8 elements per iteration. Here's the hot loop and the horizontal reduction:

	movdqu	xmm2, xmmword ptr [rdi + rsi + 16]  # load a[i+4..i+7]

Vectorizing this loop reorders the additions. That's legal for integers because integer addition is associative (wrapping is modular arithmetic at the machine level). Pass -march=x86-64-v3 to get 256-bit AVX2 (vpaddd ymm).

Deep diveUndefined behaviour is an optimization input

The optimizer assumes your program has no UB, and reasons backwards from that assumption:

int f(int* p) { int x = *p; if (!p) return 0; return x; }   // null check deleted: p was already dereferenced
for (int i = 0; i <= n; ++i) …                               // assumed to terminate; i can't overflow
bool g(int x) { return x + 1 > x; }                         // folds to 'return true'

That's why UBSan (-fsanitize=undefined) and ASan (-fsanitize=address) exist: they instrument the IR to catch these conditions at run time.

Deep diveBeyond one TU: LTO and PGO
  • Link-time optimization. With -flto, the .o files contain IR (LLVM bitcode, or GIMPLE bytecode in .gnu.lto_* sections) instead of machine code. The linker loads a plugin (that's the -plugin liblto_plugin.so in our collect2 line), merges every module and runs the optimizer over the whole program, so square can be inlined into main across files. ThinLTO keeps it parallel: it builds per-module summaries, makes global import decisions, then optimizes each module separately with the cross-module functions it imported.
  • Profile-guided optimization. Build with -fprofile-generate, run a representative workload, then rebuild with -fprofile-use. Real branch frequencies drive inlining, block layout (hot paths become fall-through), function splitting into .text.hot/.text.unlikely and register allocation. BOLT (a post-link optimizer) goes further and rewrites the final binary's layout using perf samples.

CHAPTER 08 · BACK END

Back end: instruction selection, registers and the calling convention

In brief

The back end turns IR into real instructions for one CPU. It picks instructions, fits an unlimited number of values into the CPU's 16 registers (spilling the rest to the stack), and follows the platform's calling convention: the agreed rules for where arguments, return values and saved registers go.

The calling convention is why x arrives in edi, why large return values are built directly in the caller's memory, and why every function keeps the stack 16-byte aligned.

Deep diveHow it works, in detail

The back end turns target-independent IR into real instructions for one specific CPU. In LLVM it's a long pipeline of its own, almost all of it generated from TableGen descriptions of the target: instruction formats, register classes, scheduling models and patterns.

Instruction selection

The IR %4 = mul nsw i32 %0, %0 becomes a DAG node (mul i32 a, a). TableGen patterns such as (set GR32:$dst, (mul GR32:$src1, GR32:$src2)) → IMUL32rr match it. Patterns can swallow several nodes at once: (store (add (load addr), 1), addr) becomes a single read-modify-write add DWORD PTR [mem], 1. That's exactly what we get at -O2:

$ g++ -O2 -S -masm=intel math.cpp
_Z6squarei:
	endbr64                          # CET landing pad (-fcf-protection)
	imul	edi, edi                     # x is in edi (1st int arg)
	add	DWORD PTR counter[rip], 1    # load+add+store fused into one instruction
	mov	eax, edi                     # return value goes in eax
	ret

The scheduler even moved the imul above the counter update. The two are independent, and starting the 3-cycle multiply first hides its latency.

Register allocation

LLVM's default is the greedy allocator. It computes a live interval for each virtual register (the instruction ranges where it holds a value that's still needed), assigns the biggest and hottest intervals first, and when two conflict it splits one (part in a register, part on the stack) or evicts the cheaper one. GCC uses IRA (an integrated, graph-colouring-based allocator) followed by LRA. Register allocation interacts closely with the calling convention, which pins certain values to certain registers.

The assembler and x86-64 machine encoding

In brief

The assembler encodes each instruction as bytes (1 to 15 bytes each on x86-64) and records two kinds of bookkeeping: symbols (names it defines, like main) and relocations (places it couldn't fill in, like the address of square, which lives in another file).

The result is an object file: machine code with holes in it, plus instructions for filling them.

Deep diveHow it works, in detail

The assembler (GNU as, or LLVM's integrated MC assembler) does four jobs:

  1. It encodes each instruction into bytes.
  2. It tracks the current section and an offset in each one (location counters).
  3. It builds a symbol table from labels and directives.
  4. For every reference it can't resolve itself, it emits a relocation: "patch the 4 bytes at offset 0x13 with the address of _Z6squarei once it's known".

Directives drive the bookkeeping:

Deep diveDecoding real bytes

An x86-64 instruction is 1–15 bytes in this format:

Here are bytes from the disassembly of main.o:

48 8b 05 00 00 00 00 → mov rax, QWORD PTR [rip+0] (loads greeting)

48REX.W=1: 64-bit 8bMOV r64, r/m64 0500 000 101 00 00 00 00disp32 (reloc!)

ModRM 0x05 = mod 00, reg 000 (rax), r/m 101. In 64-bit mode, mod=00 with r/m=101 means RIP-relative: the address is the next instruction's address plus disp32. This addressing mode is what makes position-independent code cheap on x86-64. The zero displacement is a placeholder that the linker patches.

89 45 ec → mov DWORD PTR [rbp-0x14], eax (stores r)

89MOV r/m32, r32 4501 000 101 ecdisp8 = −20

mod 01 (8-bit displacement follows), reg 000 (eax), r/m 101 (rbp). 0xec is −20 in two's complement. A small displacement fits in 1 byte, which is why compilers love small frame offsets.

bf 07 00 00 00 → mov edi, 7 · e8 00 00 00 00 → call rel32 · 55 → push rbp

B8+r encodes the destination register in the opcode itself (0xb8 + 7 = 0xbf, edi). The immediate is little-endian. e8 is a call with a 32-bit displacement relative to the next instruction, which is why its relocation has addend −4. 50+r is push, so 0x55 is push rbp. Writing a 32-bit register zero-extends into the full 64-bit register, so mov edi, 7 is a byte shorter than mov rdi, 7 (which needs REX.W) and just as correct.

Branch relaxation A jump to a nearby label can use eb rel8 (2 bytes) instead of e9 rel32 (5 bytes). Choosing one changes code size, which changes the distances of other jumps. Assemblers iterate to a fixed point: they start everything short and "relax" to long forms as needed. They also emit .cfi_* directives into .eh_frame as compact bytecode for "how to find the caller's frame from any PC", which exceptions and debuggers rely on.

The same code on AArch64: what's x86-specific, what's universal

In brief

Compiling the same code for ARM (AArch64) shows which ideas are universal and which are x86 quirks. ARM instructions are always 4 bytes, only loads and stores touch memory, and addresses are built in two steps (adrp then a low-12-bit offset).

The IR, the optimizer, ELF, the linker and the loader work the same way. The one difference with real consequences is the memory model: ARM reorders memory operations far more freely, so thread synchronization must be explicit.

The kernel and loader think in segments: a few large, page-aligned ranges with permissions, described by the program header table at the start. A .o has only sections. A linked executable has both, and you could strip its section table (sstrip) and it would still run.

Deep diveHow a breakpoint works

No CPU feature is needed beyond a one-byte instruction. Relocations: the to-do list for the linker

In brief

A relocation is a note left by the assembler: "at this offset, write the address of this symbol, computed this way". The linker processes these once it has decided where everything goes.

Most references on x86-64 are relative ("the target is 0x60 bytes ahead"), so they stay correct wherever the program is loaded in memory.

A relocation says: "at offset O in section X, write the value computed by formula T from symbol S and addend A". On x86-64 they're Elf64_Rela entries with an explicit addend:

  Elf64_Sxword r_addend;   // constant A
} Elf64_Rela;

Dynamic linking: PIC, the GOT and the PLT

In brief

Shared libraries like libc.so.6 are loaded at a different address in every run, and their code is shared between processes, so it can't be patched per process. Instead, code reaches anything outside itself through a per-process table of addresses (the GOT) that the loader fills in at startup.

Function calls go through a small stub (the PLT) that jumps via that table.

Deep diveHow it works, in detail

A shared library is mapped at a different address in every process, and with ASLR at a different address on every run. Its code pages are shared physically between all processes, so the code can't be patched per process. The solution is position-independent code (PIC): code never contains an absolute address. Instead it reaches:

  • Its own code and data RIP-relatively, because the distance between a library's code and data segments is fixed at link time.
  • Anything that might live in another module through a per-process, writable table of pointers, the Global Offset Table (GOT), which the loader fills in.

Function calls go through a tiny stub per function, the Procedure Linkage Table (PLT), which jumps through the function's GOT slot. Here's the real stub in our app:

Each reference in your code is resolved as early as possible. Jumps within a function are fixed by the compiler. Calls to another of your own files are fixed by the linker. Calls into shared libraries are fixed by the loader just before main runs. dlopen defers everything to run time.

At load time, the first library in search order that defines a name wins. That's how LD_PRELOAD can replace malloc.

Deep diveLoad-time lookup: the global scope and interposition

When ld.so resolves a symbol, it searches the global lookup scope: the executable first, then every DT_NEEDED library in breadth-first load order, with LD_PRELOAD libraries inserted right after the executable. The first definition found wins, even for references made from inside a library to its own exported functions. That's symbol interposition. It's what makes LD_PRELOAD=libjemalloc.so replace malloc everywhere, and it's why the compiler must call a library's own non-hidden functions through the PLT.

CHAPTER 20 · RUNNING

In brief

The dynamic loader (ld.so) relocates itself, loads the shared libraries the program needs, fills in every GOT entry, makes the tables read-only, and runs library initializers. It then jumps to the program's real entry point, _start.

_start calls into libc, which runs C++ global constructors and finally calls main. When main returns, the same path runs in reverse: destructors, flushing output, exit.

CHAPTER 23 · HARDWARE

The CPU executes it

In brief

A modern core doesn't run instructions one at a time. It predicts branches far ahead, splits x86 instructions into simpler micro-operations, runs them out of order as soon as their inputs are ready, then commits the results in the original order, so the program can't tell.

The biggest performance factor is usually memory: a cache hit takes a few cycles, a trip to RAM hundreds. Code that walks memory sequentially and keeps each thread's data apart can be many times faster.

Deep diveHow it works, in detail

The ISA (x86-64) describes a simple sequential machine that executes one instruction after another. A modern core implements that illusion with a deep, wide, speculative, out-of-order pipeline that keeps hundreds of instructions in flight. Deep diveMemory ordering, and why std::atomic compiles the way it does

x86 implements TSO (total store order): every load is an acquire and every store is a release. The one reordering it allows is a later load passing an earlier store to a different address, because stores sit in the store buffer. So atomic.load(acquire) and atomic.store(release) compile to plain mov. A seq_cst store becomes xchg (an implicitly locked instruction, which drains the store buffer), and fetch_add becomes lock xadd. Cache coherence (MESI-family protocols) keeps every core's view of a given line consistent. ARM is weaker, so the same C++ code emits ldar/stlr or dmb barriers there.

Speculation leaks Out-of-order and speculative execution are invisible to the architectural state, but not to the microarchitectural state. Squashed instructions still leave lines in the cache. Spectre (bounds-check bypass, branch-target injection), Meltdown and their successors exploit exactly this. The mitigations show up in compiled code (retpolines, lfence, -mindirect-branch), in the kernel (KPTI page-table isolation) and in microcode (IBRS, IBPB).

The OS runs your code: threads, scheduling and signals

In brief

The kernel shares a few dozen cores among hundreds of threads. Threads of one process share memory but each has its own registers, stack and thread-local storage. A timer interrupt every millisecond lets the scheduler swap threads (a context switch).

When a program touches memory it shouldn't, the CPU traps into the kernel, which turns the fault into a SIGSEGV signal.

Deep diveHow it works, in detail

Chapter 23 showed one instruction stream on one core. Real machines run hundreds of threads on a few dozen cores, and the kernel creates the illusion that each one has a CPU to itself. This machine is a good example: an Intel i9-13950HX with 32 logical CPUs on two kinds of core.

Deep diveScheduling and context switches

The scheduler decides which runnable task gets each CPU. Linux 6.6 replaced CFS with EEVDF ("earliest eligible virtual deadline first"). Each task accrues virtual runtime weighted by its nice value; among tasks that haven't had more than their fair share, the one with the earliest virtual deadline runs next. This kernel (6.8, CONFIG_HZ=1000) has a 1 ms timer tick.

spin.cpp starts 64 busy threads on 32 CPUs for 300 ms, then asks the kernel how often they were switched out:

$ ./spin

involuntary (preempted):       2090    ← oversubscribed: the scheduler time-slicing 2 threads per CPU

On a hybrid CPU the scheduler also chooses which kind of core. The CPU's Thread Director feedback ranks tasks for P-cores and E-cores, which is why a benchmark's timing can vary run to run unless you pin it with taskset. The cache benchmarks in chapter 23 pinned themselves to two P-cores (CPUs 0 and 2) for exactly that reason.

Deep diveFaults become signals

When an instruction touches memory it shouldn't, the CPU raises a page fault (chapter 22). If the kernel's fault handler finds no valid way to satisfy it, it doesn't kill the process directly. It sends the thread a signal, SIGSEGV, with details about the fault. signals.cpp installs a handler and triggers three different faults:

Talking to the kernel: from printf to pixels

In brief

A program can't do I/O itself. To print, libc executes the syscall instruction, which switches the CPU into kernel mode at a single, fixed entry point. The kernel does the work (here, writing 21 bytes to the terminal) and returns.

exit_group is the last system call, and it tears down the whole process.

Deep diveHow it works, in detail

printf formats into stdout's buffer inside libc. That buffer is line-buffered when stdout is a terminal and fully buffered when it's a pipe or file, which is why output order can change under | cat. When the buffer is flushed (at the \n here, or at exit), libc calls write(1, buf, 21), and that's where user space ends:

Finally, main returns 0, exit flushes, and the exit_group(0) system call tears down the address space. The kernel drops every VMA and frees the page tables. Pages that came from the page cache stay cached, so the next ./app starts with fewer major faults. The parent shell's wait4 returns status 0.

CHAPTER 26 · HARDWARE & OS

Hardening: the defences you got without asking

In brief

Several layers, all on by default, turn most memory-corruption bugs from "attacker runs code" into "program stops". Buffer copies are size-checked (FORTIFY). A secret value guards the return address (stack canary). Addresses are random (ASLR/PIE). Data can't be executed (NX). The GOT is read-only (RELRO). CPUs can verify jump targets (CET).

Deep diveHow it works, in detail

Many earlier chapters ran into a security feature in passing: endbr64 at the top of every function, a canary at fs:0x28, __printf_chk instead of printf, BIND_NOW and RELRO, a random load address on every run. Each one blocks a specific step of a memory-corruption exploit. Here they are in one place, with the layer that adds each one.

Deep diveWatching two of them fire

hardening.cpp overflows an 8-byte stack buffer in two different ways:

$ g++ -O2 -dM -E -x c++ /dev/null | grep FORTIFY
#define _FORTIFY_SOURCE 3
$ ./hardening f        # strcpy(buf, 32-byte string) into char buf[8]
*** buffer overflow detected ***: terminated
$ ./hardening s        # a hand-written byte loop writing 32 bytes into char buf[8]
*** stack smashing detected ***: terminated

FORTIFY works at compile time and run time together. The compiler knows sizeof(buf) == 8, so it rewrote strcpy into __strcpy_chk(buf, src, 8), which checks the length before copying. Level 3 uses __builtin_dynamic_object_size, so it also catches sizes known only at run time. A first attempt at the canary demo used memcpy(buf, src, n) with a runtime n, and FORTIFY caught that too, before the canary ever got a chance.

The canary catches what FORTIFY can't see: here, a plain loop. It doesn't prevent the overflow. It detects the damage before the function returns through a corrupted return address.

<_Z5smashPKcm>:
  sub    rsp,0x18
  mov    rax,QWORD PTR fs:0x28    # load secret
  mov    QWORD PTR [rsp+0x8],rax  # canary above buf
  …      # the copy loop writes buf[0..31]
  …      # → overwrites [rsp+8]
  mov    rax,QWORD PTR [rsp+0x8]
  sub    rax,QWORD PTR fs:0x28    # unchanged?
  jne    <fail>
  add    rsp,0x18
  ret
fail:
  call   __stack_chk_fail@plt      # abort
Deep diveStack clash protection

The guard page below a stack (chapter 24) only helps if the stack grows into it one page at a time. A function with a 100 KB local array would otherwise move rsp straight past the guard into whatever is mapped below. GCC probes every page as it allocates the frame:

_Z9big_framev:                       # char buf[100000]
	lea	r11, -98304[rsp]           # target: 24 pages down
.LPSRL0:
	sub	rsp, 4096                  # move down one page…
	or	DWORD PTR [rsp], 0         # …and touch it (faults on the guard page)
	cmp	rsp, r11
	jne	.LPSRL0
	sub	rsp, 1704                  # remainder
Deep diveChecking a binary

Without a checksec tool installed, readelf shows everything:

$ readelf -hW app_o2 | grep Type             →  DYN (Position-Independent Executable file)      PIE ✓
$ readelf -lW app_o2 | grep GNU_STACK        →  GNU_STACK … RW  0x10                            NX stack ✓
$ readelf -lW app_o2 | grep GNU_RELRO        →  GNU_RELRO 0x002db8 …                            RELRO ✓
$ readelf -dW app_o2 | grep FLAGS            →  FLAGS BIND_NOW · FLAGS_1 NOW PIE                full RELRO ✓
$ readelf -nW app_o2 | grep feature          →  x86 feature: IBT, SHSTK                         CET-compatible ✓
$ readelf --dyn-syms -W app_o2 | grep _chk   →  __printf_chk@GLIBC_2.3.4                        FORTIFY ✓
"Compatible" isn't the same as "enforced" The IBT, SHSTK property only says the binary was built to work with Control-flow Enforcement Technology: every indirect-branch target starts with endbr64, and returns are well behaved. Whether the CPU actually enforces it depends on the hardware, the kernel (user-space shadow stacks arrived in Linux 6.6) and glibc's settings, and every loaded library must be marked compatible too. One unmarked library disables it for the whole process.
Opt-in extras worth knowing -D_GLIBCXX_ASSERTIONS turns on bounds checks for std::vector::operator[] and friends. -ftrivial-auto-var-init=zero zero-fills uninitialized locals. -fsanitize=address,undefined is far stronger but too slow for production. -D_FORTIFY_SOURCE=3 needs -O1 or higher to do anything, since it relies on the optimizer's object-size analysis.
